What the data looks like today

Dylan screen-shared Snowflake and queried the raw tables. Dev has around 37 million rows in the raw table; Integration was also pulled up. The raw tables are the unprocessed event payloads directly from Kafka — these are not what we're targeting for load testing.

There was a brief clarification about the layer terminology: raw/bronze is the bottom, business/silver is processed above that, and gold is the final analytics-ready layer in ClickHouse. The gold tables are the target.

Proto schemas: all seven topics have Protobuf schemas downloaded from Confluent Schema Registry. They live in ipa-topic-schemas/ and define the field shapes for each event type. Each schema has a top-level envelope message with a oneof data covering the sub-event variants for that topic.
The kafka-generator repo

Dylan introduced a new repo he built on Friday — a Kafka event generator. It was built from scratch rather than extending the existing chKafka tooling, which had too much baggage. The generator can send synthetic Protobuf events to Kafka topics on a schedule.

Dylan mentioned he has a couple of pending PRs on this repo that need to be merged before it's fully usable — specifically the feature-data-layer-topics branch. Those are getting merged that afternoon.

The generator currently doesn't do sophisticated data sampling (i.e., it doesn't derive realistic value distributions from existing event data). That was flagged as a potential future improvement, particularly useful for load testing.

Two approaches for getting data into ClickHouse

The team talked through two ways to populate the gold tables with enough volume for load testing:

  • Kafka path — use the kafka-generator to push synthetic events into the Kafka topics running in sandbox, then let the ClickHouse Kafka Connector consume those topics and write to the gold tables. Useful for testing the full connector pipeline and validating connector behavior end-to-end (e.g., reproduce a bug with the old connector version, then confirm the fix with the new version). Dylan noted the EAM streaming appliance is already running in sandbox and reading off topics without errors.
  • Direct SQL path — bypass Kafka entirely. Use the proto schema shapes (and optionally a CSV sample from Snowflake as a realism reference) to generate a large file of SQL INSERT statements or CSV data, then load it straight into the sandbox ClickHouse Cloud instance. Faster to get volume in, since the end goal is data in ClickHouse.

The direct SQL path was agreed on as the approach for load testing. The infrastructure can be reused or ported into the kafka-generator repo later if the Kafka path is also needed.

What was built: a Python script generate_data.py was written this session. It generates batched INSERT SQL or CSV for all seven gold tables based on the proto schemas, with no external dependencies. Defaults to 1M rows per table (~8 min). Column names are inferred from the proto field names — verify against the actual ClickHouse DDL before loading.
Manual mode for one-off events

A specific request came up for a "manual mode" — a way to fire a single synthetic event at a Kafka topic on demand, rather than running a continuous stream. The use case is targeted connector regression testing: send one event, confirm it lands correctly in ClickHouse, repeat with variations. This wasn't built yet and was noted as a follow-on item.

Target environment

The sandbox ClickHouse Cloud instance is the safe place to do all of this work. Dev and Integration environments are not to be touched. Dylan confirmed the sandbox should be safe — it's only used by the team. The goal is to get enough volume in there to run meaningful queries across silver and gold and test query performance.

The option of spinning up a local ClickHouse instance in the clusters was briefly mentioned but dismissed — no reason to do that when the cloud instance is available.
